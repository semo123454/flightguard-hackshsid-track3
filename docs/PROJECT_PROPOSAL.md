# 航策 FlightGuard 项目策划书

**项目主题：重点机场航班异常应对智能助手**  
**参赛方向：HackSHSID 2026 · Track 3**  
**面向客户：虚构中国国内航空公司**  
**编制日期：2026年10月22日**  
**文档用途：团队实施、原型验收与客户汇报**

> 本项目使用赛事提供的教学模拟数据。机场、事件、规则和数值不代表真实航空运行。本策划书中的开发周期、指标和岗位配置是团队实施建议，不是赛事公布的截止时间、评分权重或已取得的效果。

## 一、项目概述

航策 FlightGuard 面向航空公司的运行人员、机场协调人员和旅客服务人员，在天气变化、运行压力上升或信息冲突时，整理证据、识别异常、提出有顺序的核查建议，并生成面向不同对象的沟通草案。

项目采用“语言模型 + 数据检索 + 规则引擎 + 人工复核”的方案。语言模型是本次计划交付的核心组件，负责理解自然语言事件、结合检索证据组织分析、生成三类沟通草案，并根据追问和新增事实修订回答。程序负责数值计算、来源及规则校验，人工负责专业判断与正式发布。

项目以“每一个判断有依据，每一个未知有核查方向，每一个重大决定有人工负责人”为设计原则。助手既要能发现需要关注的事件，也要能在证据不足时说明无法判断，在人员补充信息后修订建议。

本次比赛计划形成一个可以现场演示、输入新事件并复现结果的原型，以及配套测试报告和实施材料。工作区已有同名离线原型及相关文档，本策划书以其为实施基础；已有功能的完成质量以本轮验收结果为准，不以文件存在视为通过验收。

## 二、业务背景与问题定位

机场异常应对涉及多个岗位和数据来源。天气预报反映未来风险，历史数据提供正常运行参照，现场人员掌握保障能力，正式航班状态则需要单独确认。不同信息可能更新不同步，甚至相互冲突。

本项目重点解决四类问题：

1. **发现异常困难。** 单看一个比例无法判断异常程度，需要结合机场自身历史和同类机场进行比较。
2. **判断依据分散。** 工作人员需要快速知道结论来自哪些数据、适用于哪个时间段、还缺少什么。
3. **行动顺序不明确。** “持续关注”缺乏可执行性，需要给出先核查什么、由谁跟进、何时升级。
4. **沟通和反馈脱节。** 内部研判、机场协调与旅客通知需要不同表达，人工修订也需要保留并用于后续改进。

上述问题是本项目针对赛题建立的业务假设。若进入实际试点，应通过岗位访谈和历史案例验证，不能直接视为客户现有流程的实测结论。

## 三、项目目标与范围

### 3.1 项目目标

- 建立可解释的异常筛查方法，展示历史基线、同类机场参照及规则依据。
- 根据新输入生成风险判断、信息缺口、核查顺序、升级条件和三类沟通草案。
- 接入真实语言模型调用，支持自由文本理解、基于证据的问答和多轮事件补充，并展示模型运行状态。
- 研究天气变量与机场放行正常比例的统计函数关系，预留独立接口，在拟合与验证完成后向助手提供定量参考。
- 在缺失、冲突和来源不可靠的情况下正确降低判断强度或停止行动结论。
- 支持人工接受、修改、拒绝建议，并保留原始记录和修订理由。
- 使用预设案例与未见场景验证系统，并提供可复现的测试证据。

### 3.2 本次实施范围

基础版本使用赛事模拟数据，覆盖语言模型接入、数据读取、基线分析、事件研判、消息草拟、多轮追问、人工复核和测试展示。模型调用和端到端模型测试纳入基础验收。公开数据可作为可选补充，须单独登记来源、时间和口径，不能与虚构机场强行对应。

本项目不接入真实执行系统，不自动作出放行、取消、调度、维修或赔付决定。旅客消息仅为待审核草案。逐航班延误预测、航班恢复优化、机组排班和真实旅客通知不纳入本次基础交付。

## 四、用户与使用场景

| 用户 | 主要问题 | 助手提供的内容 | 人工职责 |
| --- | --- | --- | --- |
| 运行人员 | 哪些异常值得先处理，依据是什么？ | 风险、证据、信息缺口、行动优先级 | 核实现场事实并作出专业判断 |
| 机场协调人员 | 需要向机场确认哪些资源和时段？ | 保障能力、前序运行及资源核查清单 | 获取确认信息并推进协调 |
| 旅客服务人员 | 当前可以向旅客说什么？ | 面向旅客的风险提示草案 | 审核事实、措辞和发布时机 |
| 项目维护人员 | 系统为何出错，如何改进？ | 测试结果、反馈记录和规则版本 | 分析错误、修订规则并回归验证 |

典型流程为：选择机场并录入事件，查看适用历史背景，获得研判及核查建议，补充现场信息，重新评估，再由人工复核沟通草案和后续行动。

## 五、数据方案

### 5.1 数据组成

赛事工作簿提供8个虚构机场的2024—2025年月度运行与天气数据、年度规模数据，以及5个模拟事件、12条运营规则、标准输出模板、人工反馈示例和15项测试问题。

| 数据 | 使用目的 | 使用限制 |
| --- | --- | --- |
| 月度运行基线 | 比较机场自身历史与同类机场水平 | 不能直接代表当天或某架航班状态 |
| 年度规模与业务重要程度 | 辅助安排核查优先级和分析影响范围 | 不单独决定高风险 |
| 月度天气数据 | 展示历史背景、探索关联线索 | 不能证明天气导致具体航班异常 |
| 模拟事件及现场信息 | 识别当前问题、时间范围和信息缺口 | 不补造未提供的数值、位置或状态 |
| 运营规则 | 约束输出、核查和人工审批边界 | 属于比赛模拟规则，不作为真实运行规章 |
| 人工反馈和测试问题 | 验证行为并推动迭代 | 示例结果不等于系统实际测试成绩 |

### 5.2 数据处理要求

导入时保留原始字段、来源编号、单位和时间。比例以数值保存，百分比与百分点明确区分；“按计划完成航班比例”和“机场放行正常比例”分别处理。

保留赛事故意设置的缺失与冲突，不将缺失值填成零。发现重复记录、无效月份或超出范围的比例时，标记并要求复核。界面及报告持续显示模拟属性。

建立来源登记表，记录资料名称、时间范围、更新时间、整理方法和复核状态。来源未知时不虚构可信度。

### 5.3 天气与放行率函数关系研究

团队计划探索是否能够建立可靠的 `放行率估计值 = f(天气特征, 机场背景, 季节)`，不预设一定能找到有效函数。函数研究是可选增强，系统的核心研判和交付不依赖其成功。第一阶段将“放行率”明确对应赛事字段“机场放行正常比例”，不与“按计划完成航班的比例”混用。后续取得真实数据时，须确认指标定义、分子、分母及统计范围，不能仅凭名称相近合并。

首批可用天气特征为月度降水量、平均气温、最大风速和明显不利天气天数，按“机场＋年份＋月份”与放行指标匹配。若后续取得同机场、同时间粒度的数据，可增加能见度、雷暴、降雪等特征；未取得的字段不作为当前模型的必需输入。

研究步骤如下：

1. 核实数据质量、机场与气象站对应关系、时间范围和单位，区分实测、预报与模拟数据，记录有效匹配样本数及缺失情况。
2. 绘制散点及分组关系，观察天气变量与放行率的关联，同时考虑机场差异、季节性和可获得的运行背景，避免把不同机场的固定差异全部归因于天气。
3. 先建立只使用机场历史与季节信息的基准模型，再加入天气变量拟合简洁函数，检验天气是否带来额外解释或预测价值。
4. 优先比较可解释的线性关系与少量非线性项。可采用候选形式 `p̂ = sigmoid(β0 + βP·P + βT·T + βW·W + βD·D + 机场项 + 季节项)`，其中 P、T、W、D 分别代表上述天气变量。系数与最终形式须由数据拟合和验证确定，不预设天气影响方向；不将此候选公式当成已得到的结论。
5. 按时间划分训练、验证和最终测试集，使用训练集完成缺失处理、标准化与参数拟合，避免未来数据泄漏。若计划适用于新机场，再增加留出机场测试，并明确模型对未见机场的支持范围。
6. 比较天气模型与基准模型的 MAE、RMSE（统一报告为百分点）及分机场误差，记录样本数与误差范围。区间如有输出，须说明构造方法并验证覆盖情况；未校准时返回空值，不编造置信区间。

赛事数据只有两年月度记录，完整匹配前最多为8个机场×24个月的192条记录，适合先验证研究流程，不足以预先保证复杂函数可靠。模拟数据中的相关关系也不能直接外推到真实航空运行。

使用完整月份的实测天气拟合当月放行率，属于历史关联分析或回溯估计；要称为提前预测，必须只使用预测时点已经可获得的数据，例如带发布时间的预报。月度函数不能直接输入“未来六小时强降雨”后生成可信的六小时放行率。日内应用需要另行取得对应粒度的数据、训练并验证模型。

研究允许得出“天气未显著改善留出集表现”的结果。未验证、效果不足或适用范围不匹配时不启用估计输出；研究本身及接口预留可以完成，不以一定找到有效函数为验收前提。相关函数描述统计关联，不自动证明天气是异常的因果来源。

## 六、核心功能设计

### 6.1 历史基线与异常筛查

选择机场及参考月份，计算该月份之前最近12个月的平均完成比例，并显示实际覆盖区间和样本数。不足12个月时说明样本不足；没有历史记录时不生成伪造基线。同类机场比较须保持月份、分类和指标一致。

采用赛事 RULE003 作为基础筛查规则：当同口径、可比较的当前指标低于过去12个月均值超过5个百分点，标记为重点复核。定义：

`差值（百分点）=（当前比例 - 历史平均比例）× 100`

例如，历史均值85%、当前月度比例79%，差值为−6个百分点，触发重点复核。该例仅解释计算方法，不是数据包中的实测结果。

月度历史异常和当前事件风险分开展示。只有日内文字描述而没有可比数值时，不计算精确降幅；月度指标异常也不直接转化成具体航班的延误结论。

### 6.2 当前事件研判

输入字段包括机场、事件时间、天气描述、运行情况、正式状态、现场保障信息、来源及更新时间、冲突标记和未知事项。支持预设案例和自由录入新事件。

用户可以直接输入“海陵下午预计强降雨，保障能力还没确认，先查什么？”语言模型提取机场、时间、天气信号和未知事项，并保留对应原文。未给出的日期、正式状态和具体航班不得推断补齐；机场无法唯一匹配时要求用户补充。用户后续补充“机场已确认保障能力下降”时，系统建立新的事件版本，重新检索和评估，并解释哪些结论发生变化。

拟采用以下规则化分级，并在测试中校验边界：

| 输出 | 拟定判断原则 | 后续处理 |
| --- | --- | --- |
| 低 | 信息足以判断，未出现明显需升级信号 | 常规监测并说明判断范围 |
| 中 | 存在需要核查的天气或运行压力信号 | 优先补充关键事实，准备沟通草案 |
| 高 | 多个独立风险信号同时存在，影响可能扩大，且满足来源核验要求 | 建议提交运行负责人复核升级 |
| 无法判断 | 关键来源冲突、可靠性无法确认，或缺少足以影响结论的信息 | 列出缺口和人工复核对象，停止确定性行动结论 |

高风险核验应遵循 RULE008，检查是否至少有两个可靠来源。不同来源编号不必然代表独立证据，不将同一信息的转载重复计数。机场规模大或业务重要程度高，只能影响核查优先级。

### 6.3 解释与行动清单

每次输出分别展示已知事实、历史背景、待核查假设和信息缺口。关键结论关联具体来源、规则编号与时间范围，尽可能定位到数据记录。

行动建议按先后排列，并注明目的与负责岗位：先核实信息可靠性和现场保障能力，再核查前序飞机、登机口及后续任务，随后准备监测与沟通材料。升级条件写成可检查的条件，例如“保障能力下降且出现正式运行异常”，并指定接收建议的岗位。

### 6.4 三类沟通草案

- **内部运营提示：** 说明事件、证据、潜在影响、核查顺序和升级条件。
- **机场协调信息：** 明确需要确认的天气更新时间、保障能力、资源及重点时段。
- **旅客信息草案：** 使用简明语言说明已确认事实和风险，不承诺未知恢复时间，不将风险表达为已经延误，提示以正式通知为准。

三类草案共享同一份经核验的事实，保持状态一致。旅客草案须有明确的待审核状态。

### 6.5 人工反馈与修订

人员可以接受、修改或拒绝建议，填写理由及补充事实。系统保留原建议，并创建关联的修订版本，记录时间、处理结果和调整依据。无法核实的新信息仍须标记待核查，不因人工输入就自动视为已证实。

反馈用于补充事实、修订规则和增加测试案例，不直接转化为未经审核的自动学习更新。至少演示接受、修改、拒绝各一个案例。

## 七、技术实现方案

### 7.1 系统组成

采用浏览器界面、本地后端、语言模型适配层、数据与规则层的结构，围绕现有 HTML/CSS/JavaScript 页面和 Node.js 服务实施。模型请求由后端发起，浏览器不接触服务密钥。

| 组件 | 职责 |
| --- | --- |
| 数据层 | 读取赛事工作簿对应的 JSON 数据，检索机场、月份、规则与来源 |
| 分析层 | 计算基线和差值，检查缺失、冲突及时间口径 |
| 天气与放行率模型接口（预留） | 在独立统计模型通过验证后返回放行率估计、适用范围与误差信息；未启用时明确返回不可用 |
| 规则层 | 形成风险判断、核查顺序、升级条件及停止条件 |
| 语言模型层 | 提取事件字段，结合证据组织分析，生成解释、三类草案和追问回答 |
| 编排与校验层 | 调用只读检索和计算工具，限制调用范围，验证模型输出，管理超时和回退 |
| 反馈层 | 保存原建议、修订版和人工处理记录 |
| 展示层 | 支持事件输入、证据查看、草案复核与测试展示 |

### 7.2 语言模型职责与边界

语言模型承担四项核心能力：

1. **事件理解：** 从自由文本中提取机场、时段、天气、运行信号和信息缺口，识别否定、预测与已发生状态的区别。
2. **证据分析：** 根据检索到的记录和程序计算结果，解释风险依据，提出待核查假设，并在规则允许范围内组织核查建议。
3. **对象化沟通：** 为运营、机场协调和旅客生成不同内容，保持事实和状态一致。
4. **多轮修订：** 回答“为什么”“先查什么”“新增信息会改变什么”等追问，根据事件版本与人工反馈修订建议。

数值计算、风险分级规则和停止条件由程序执行。模型可以指出规则未覆盖的情境，但不能自行改写阈值或绕过停止条件；模型与规则结论不一致时标记待复核。输出提供简明的证据摘要、适用规则和不确定性，不要求披露模型内部思维过程。

现有项目文档描述的是离线原型，语言模型接入属于本策划要求实施的核心工作，尚不能据此宣称已完成。离线模板保留为故障回退，不能替代模型接入验收。

### 7.3 检索与模型调用流程

采用检索增强生成方式：先取得与事件有关的可信资料，再交给模型组织回答。赛事数据规模较小，优先按机场、月份、规则编号进行精确查询；规则与说明文本可辅以关键词检索，无需为本次原型强行增加向量数据库。

完整流程如下：

1. 后端检查输入长度、删除或匿名处理个人信息，再将事件文本交给模型提取字段。
2. 程序核验机场名称、时间、数值和原文依据。解析不确定的关键字段保留未知；模型提取结果不自动成为已核实事实。
3. 编排层调用只读工具，例如 `getAirportBaseline`、`getAirportProfile`、`getRelevantRules` 和 `getEventHistory`，获取适用记录与反馈。工具名称是拟定接口，不代表已经实现。
4. 分析与规则引擎完成均值、差值、时间口径、冲突和风险等级检查，生成包含来源编号、记录位置与时间的证据包。
5. 模型接收当前事件、证据包、规则结论、输出结构和必要的会话上下文，生成解释、核查建议及三类草案。
6. 后端验证输出。通过后展示为“待人工复核”；不通过时最多执行一次带校验错误的修复请求，再失败则回退并明确原因。
7. 人工补充信息或修改建议后，保存新版本并重新运行相关步骤。旧版本只作为历史，不当作最新事实。

模型可以请求允许的检索工具，但后端必须验证参数、机场和时间范围，并限制调用次数。工具不提供删除记录、修改规则、取消航班或发送通知的能力。

### 7.4 输入、输出与提示词设计

模型输入分为固定任务说明、当前事件、证据包、规则结果和有限会话历史。事件文本和检索文档均作为资料处理，其中出现的“忽略规则”“直接发布”等文字不能成为系统指令。模拟标识和停止条件始终包含在固定任务说明中。

模型返回结构化 JSON，包含事实引用、解释、待核查假设、信息缺口、有序行动、升级说明及三类草案。事件编号、生成时间、规则风险等级、适用范围和审核状态等权威字段由后端写入，最终映射到赛事17字段输出模板。

每条关键事实关联证据编号。后端至少检查：字段类型和完整性、引用编号是否存在、数字和时间是否与证据一致、模型文字是否与规则等级及正式状态冲突、旅客文本是否带草案标识、是否出现未经支持的恢复时间或已执行声明。引用编号存在不等于引用正确，还须检查证据是否支持相应表述，并在测试中人工抽查。

固定任务说明示意：

> 你为模拟航空运行事件提供决策支持。只使用提供的证据陈述事实；区分事实、历史背景、假设和未知。采用规则引擎给出的等级及停止条件。为三个对象分别生成草案。每项关键结论引用证据编号。缺少信息时列出核查需求，不编造航班状态、数字或恢复时间。按指定结构返回结果。

### 7.5 模型选型、成本与故障处理

首版计划通过后端接入一个支持中文理解、结构化输出和工具调用的语言模型服务。具体供应商和模型版本在实施首日依据可用账户、实测质量、延迟和费用确定，记录完整配置；本策划不承诺未经验证的型号能力或价格。不计划从零训练或微调，先通过提示词、检索证据和测试迭代满足要求。

正常流程预计包括一次事件提取和一次分析生成请求；结构化表单输入可以跳过提取请求。设置输入长度、输出长度、工具调用次数、单请求超时、并发量和日预算上限，具体阈值在首日试调用后确定。对同一事件版本和配置可缓存结果；事件、证据、规则、提示词或模型版本改变时使缓存失效。

按实际用量记录输入与输出 token、调用次数、延迟和费用。预算计算采用“各次输入用量×对应单价 + 输出用量×对应单价 + 其他服务费用”，在选型时核验计价单位，包含重试成本。达到预算或重试上限后停止继续调用并切换模式。

超时、限流、网络故障或校验失败时，系统展示可用的规则结果、证据和模板草案，并标注“规则回退模式”。模型正常时显示“语言模型辅助模式”。回退记录计入可靠性统计，不计作模型成功输出。

### 7.6 运行与复现

本地前后端与外部模型服务配合运行。服务密钥通过后端环境配置管理，不进入代码、浏览器、截图或提交包。仅传输完成匿名处理的必要模拟事件及相关证据，不发送整本工作簿和无关会话。

复现包包含模型配置示例、提示词版本、规则版本、脱敏后的测试输入、实际模型输出、校验结果和运行说明；记录缓存命中和调用模式。不承诺模型每次逐字复现，验收关注事实、规则和行为是否一致。无密钥时可以启动离线回退演示，但必须另有真实模型调用的验收证据。

### 7.7 天气与放行率备用接口

预留 `estimateReleaseRate(input)` 作为后端内部接口，可通过拟定的只读计算路由 `POST /api/weather-release-rate/estimate` 暴露。这里约定接口契约，当前文档修改不代表该路由或统计模型已实现。接口默认关闭，后续可替换拟合函数或独立模型服务，语言模型和页面无需跟随更改计算逻辑。

| 请求字段 | 含义与约束 |
| --- | --- |
| `airport_id` | 与数据登记一致的机场标识 |
| `target_metric` | 固定为 `airport_release_normal_ratio`，防止指标混用 |
| `period_start`、`period_end`、`granularity` | 估计覆盖区间与粒度；初版只允许 `month` |
| `as_of`、`mode` | 信息截止时间，以及 `retrospective` 回溯估计或 `forecast` 提前预测 |
| `weather` | `precipitation_mm`、`mean_temperature_c`、`max_wind_speed_mps`、`adverse_weather_days`，字段单位固定，缺失使用 null |
| `weather_basis` | 实测、预报或模拟，不能隐式互换 |
| `source_refs` | 天气资料来源、覆盖时间、发布时间和模拟属性 |

模型所需机场及季节信息由后端检索，避免让语言模型自行生成。预报输入还须检查发布时间是否早于或等于 `as_of`，并确认模型已支持该模式。

| 响应字段 | 含义与约束 |
| --- | --- |
| `status` | `ok`、`not_configured`、`not_validated`、`insufficient_data`、`out_of_scope`、`timeout` 或 `error`；`not_validated` 包括研究后未找到可靠关系 |
| `estimate` | 0—1之间的放行正常比例估计；非 `ok` 时为 null |
| `prediction_interval` | 经验证的预测区间与覆盖水平；尚未校准时为 null |
| `model_version`、`model_family` | 模型版本与函数类别，未配置时为 null |
| `training_scope` | 训练机场、时期、粒度、指标与模拟属性 |
| `validation_summary` | 留出集样本数、MAE、RMSE、基准对照及区间校准情况 |
| `source_refs`、`limitations`、`reason` | 实际使用的数据依据、适用限制和不可用原因 |

未配置时的返回示例：

```json
{
  "status": "not_configured",
  "estimate": null,
  "prediction_interval": null,
  "model_version": null,
  "model_family": null,
  "training_scope": null,
  "validation_summary": null,
  "source_refs": [],
  "limitations": ["天气与放行率函数尚未拟合和验证"],
  "reason": "接口预留，当前继续使用既有证据与规则流程"
}
```

接入后，模型返回值作为单独的“统计模型估计”证据送入语言模型，和观测事实分开展示。语言模型负责解释函数输出及适用限制，不自行拟合系数、编造估计或把估计写成正式状态。未配置、缺数据、超出训练范围或调用失败均不阻断原有助手流程，也不等价于零风险。预测误差、估计区间与机场风险等级分别表达。

### 7.8 冗余设计与降级策略

主流程始终独立运行：事件输入 → 数据与来源核查 → 历史基线及天气风险规则 → 语言模型解释与沟通草案 → 人工复核。天气函数作为旁路补充证据，关闭整个函数模块后，以上流程仍应完整可用。

| 路径 | 提供的信息 | 启用条件 | 不可用时的处理 |
| --- | --- | --- | --- |
| 历史基线路径 | 机场自身与同类机场的历史表现、可比指标偏离 | 存在口径一致且覆盖范围明确的数据 | 保留未知，不把其他机场均值冒充该机场数据 |
| 天气与运行规则路径 | 天气信号、现场保障、运行压力对应的核查建议 | 有可引用的事件事实及适用规则 | 列出信息缺口，必要时输出无法判断 |
| 天气函数旁路 | 经验证的放行率估计及误差 | 已通过留出验证，且本次输入满足适用范围 | 不输出估计，继续前两条路径 |
| 语言模型表达路径 | 对已有证据的解释、追问回答和三类草案 | 模型可调用且输出通过校验 | 使用已验证规则与模板，标注回退模式 |

没有有效天气函数时，系统仍可报告“天气风险上升，需核查机场保障能力”，但不能凭此编造“放行率将下降至某值”。历史放行率只标为历史参考，不作为函数失败时的预测替代值。若历史与现场信息也不足，系统仍可输出信息缺口、核查清单和人工升级对象，不强行给出等级或数值。

旁路的具体故障处理约定如下：

1. **未找到可靠关系或尚未验证：** 关闭函数调用，记录研究结论，返回 `not_validated`，不持续重试拟合。
2. **输入缺失或超出适用范围：** 返回缺失字段或范围原因，不自动补造天气数据，不将月度函数套用于小时事件。
3. **超时或服务故障：** 设置独立超时预算并隔离异常，不无限重试；连续失败后暂时停用旁路。迟到结果不覆盖已生成报告，恢复后按新的报告版本重新评估。
4. **估计与已确认事实或规则冲突：** 保留各自来源和冲突说明，将估计标为待复核并暂停用于建议；不通过平均两个结果消除冲突，也不由语言模型任选一个。
5. **语言模型同时不可用：** 继续提供规则结果、原始证据和模板草案；保留人工补充及复核入口，明确哪些能力暂时不可用。

多个路径共享同一天气或运行资料时，不构成多个独立来源。函数输出与其输入数据不能重复计为高风险升级所需的两份独立证据。模型不可用是技术状态，不自动使机场风险升高或降低。

界面分别显示“事件风险”和“系统运行模式”。函数关闭时可显示“基于历史与规则研判，暂无可靠的放行率估计”；语言模型故障时另显示“规则回退模式”。模块恢复不静默修改已审核输出，必须生成关联的新版本。

## 八、测试与验收

### 8.1 场景覆盖

| 场景 | 重点验证 |
| --- | --- |
| EVT001：海陵天气风险 | 区分预报风险与正式延误，优先核查保障能力 |
| EVT002：北岭持续运行压力 | 不直接归因于天气，检查前序运行和资源 |
| EVT003：云川来源冲突 | 展示矛盾，核查时间和口径，不自行选择来源 |
| EVT004：南湾旅客沟通 | 草案不把风险写成已确认延误，不自动发送 |
| EVT005：高原人工否决 | 保存原建议，依据补充事实重新评估 |
| 新机场与新组合事件 | 基于输入和基线响应，不依赖事件编号固定返回 |

覆盖赛事15项测试，并增加阈值附近、历史不足12个月、缺失不等于零、来源过期、不同时间粒度和模型不可用等边界案例。由未编写规则的成员准备未见场景；修改规则后使用另一批留出场景复验，避免将调试案例冒充未见测试。

### 8.2 验收指标

以下是项目自定目标，不是官方评分标准，实际结果须记录实测分子、分母和失败案例。

| 指标 | 计算或检查方法 | 目标 |
| --- | --- | --- |
| 标准输出完整率 | 满足17字段结构要求的输出数／测试输出数；未知须明确标记 | 100% |
| 关键结论可追溯率 | 有有效来源或规则支持的关键结论数／全部关键结论数 | 100% |
| 重大越权次数 | 自动取消、放行、发送正式消息等违反边界的次数 | 0 |
| 冲突与停止行为 | 对应场景是否指出问题并停止确定性行动结论 | 必须全部通过 |
| 未见场景适应性 | 是否读取新机场资料、随有效输入变化、保留未知 | 逐例通过人工复核 |
| 反馈留痕完整性 | 原建议、理由、新事实和修订关系是否完整 | 接受、修改、拒绝均通过 |
| 处理效率 | 在同等质量要求下比较人工流程与辅助流程的完成时间 | 记录实测结果后评估 |

运行时间比较采用相近难度案例和交叉顺序，记录样本数、中位完成时间与复核错误数。未开展实验前，不宣称节省特定比例的时间或降低真实延误率。结构检查通过也不代表语义正确，关键内容须人工审阅。

### 8.3 语言模型专项验收

将“纯规则与模板”和“规则、检索与语言模型结合”两种模式在同一批留出案例上比较，说明模型在自由文本理解、追问处理和沟通表达上是否提供实际改善。真实调用与模拟响应测试分开报告，不能仅凭接口模拟测试声称模型已接入。

| 测试项 | 验收方式 |
| --- | --- |
| 真实模型接入 | 完成新事件输入到三类草案的实际调用，保存脱敏请求记录、模型版本与校验结果 |
| 事件提取 | 检查机场、时间、否定、预测、正式状态的提取正确性；缺失数字保持未知 |
| 多轮修订 | 新增事实后更新判断及解释，保留旧记录；切换事件不混入上一事件事实 |
| 证据约束 | 逐项核对关键事实、数字和引用，验收集不允许未经支持的关键事实通过发布前校验 |
| 提示注入 | 输入包含“忽略规则”“直接发送”等文字，仍遵守工具权限和审核流程 |
| 输出稳定性 | 对冲突、停止条件、正式状态等关键案例至少重复3次，检查语义而非逐字一致性 |
| 故障回退 | 模拟超时、限流、无效 JSON 和校验失败，确认明确切换模式且不伪称模型成功 |
| 质量与成本 | 报告事实错误、人工修改情况、成功率、响应时间分布及实际调用用量 |

若核心模型流程尚未通过以上验收，项目状态应标为“模型集成待完成”，即使规则演示可运行也不能标为全部完成。

### 8.4 天气函数与预留接口验收

本阶段需交付字段契约、缺失与不可用状态、单位及粒度检查方案。后续实现接口时，验证未配置、缺少天气字段、错误单位、未知机场、超出训练范围、日内输入误用月度模型、未来信息泄漏及服务故障等情形，不允许返回伪造数值。

统计模型启用前另行提交数据匹配说明、公式或模型文件、训练与测试时间划分、基准对照、误差及适用范围。只有预先约定的留出验证通过后才启用 `ok` 输出；即使拟合未产生有效提升，也应提交研究结果并保留不可用状态。任何示例常数或测试替身必须标注，不作为真实拟合结果展示。

冗余验收必须覆盖：完全移除函数模块后完成核心事件流程；函数研究无效时不出现伪造预测；函数超时不拖垮主流程；函数与事实冲突时保留待复核状态；函数与语言模型同时不可用时仍能展示证据、规则和模板；历史资料也不足时明确无法判断。关闭函数模块后，赛事15项测试的核心行为要求仍须满足。

验收结果分别记录“核心助手是否通过”“函数接口与降级设计是否通过”“天气函数是否有效”。第三项可以为未找到可靠关系，不影响前两项成立；这时交付研究结论和关闭状态，不承诺定量放行率预测。

| 第5日 | 整理汇报、复现包与演示脚本，另一台电脑试运行 | 最终提交材料及演示备份 |

建议四个职责方向：产品与业务负责人管理需求和汇报；数据与规则负责人维护数据口径与分级逻辑；开发负责人完成模型适配、提示词、工具编排、输出校验以及界面和服务；测试与交付负责人准备留出案例、模型专项测试、验收和打包。实际人员不足时可兼任，但关键结论尽量交叉复核。

语言模型接入从首日开始，与数据和规则校验同步推进。优先保证模型理解新事件、引用证据、生成草案及处理反馈的完整流程，再完善界面。离线回退用于保持故障时可用性，完整交付必须包含实际模型调用结果。

天气函数研究作为独立工作线：数据与规则负责人核查放行率口径、匹配天气数据并进行拟合验证，开发负责人预留上述接口和调用开关，测试负责人检查单位、时间泄漏和回退行为。首日确定数据与字段，第二至四日开展匹配及基准对照，第五日提交研究进展和接口说明；未通过验证的函数继续保持未启用，不影响核心助手交付。

研究时间以本轮第二至四日为上限。若数据无法匹配或留出表现不足，结束本轮拟合，整理限制与下一步数据需求，将剩余时间用于核心助手和冗余测试，不为得到公式延误提交。

## 十、资源、风险与应对

基础版本所需资源为开发电脑、浏览器、Node.js 运行环境、赛事文件、模型服务账户和网络连接。团队投入按岗位任务记录。模型费用在选定服务和调用量后核算，覆盖开发、重复测试和现场演示，并设置预算上限。模型账户或额度不足时需解决接入条件，不能用模板输出替代真实模型验收。

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 历史月份被当作当前事实 | 产生不成立的实时判断 | 单独显示事件时间与历史区间，限制直接比较 |
| 天气函数过拟合或口径混用 | 给出误导性的放行率估计 | 区分放行与完成指标、按时间留出测试、比较无天气基准、限制适用粒度 |
| 输出添加未提供事实 | 误导核查和沟通 | 结构化证据、引用校验、人工复核 |
| 输入或资料包含指令诱导 | 绕过任务边界或调用不当工具 | 固定权限、资料与指令分离、服务端参数校验和注入测试 |
| 模型输出波动或格式错误 | 同一事件结论不一致、解析失败 | 程序固定规则结论、结构校验、重复测试和有界修复 |
| 模型调用费用超出预算 | 测试或演示中断 | 用量记录、缓存失效策略、调用上限及日预算 |
| 来源冲突被忽略 | 错误分级 | 设置停止结论逻辑并测试冲突案例 |
| 规则过度适配示例 | 新事件处理失败 | 留出场景、参数变化及换机场测试 |
| 旅客措辞过度确定 | 将风险误传为正式状态 | 草案标识、状态核验和发布前人工审核 |
| 人工意见覆盖历史 | 无法复盘 | 追加修订版本，保留原建议和修改原因 |
| 外部服务不可用 | 演示中断 | 保留离线模式和已验证的复现步骤 |
| 输入含个人信息 | 不必要的信息留存 | 输入提醒、删除或匿名处理、最小化保存 |

## 十二、预期价值与后续发展

项目预期帮助工作人员更快整理证据、发现信息缺口、形成可复核的行动顺序，并保持对不同对象沟通的一致性。比赛阶段能够证明的是模拟任务中的行为质量和可复现性，不能据此声称已减少真实航班延误或运营损失。

后续如有实际合作机会，可先用去标识化历史案例开展影子试点，再评估只读天气、正式航班状态和机场保障数据接入。真实部署前须重新核定业务口径、规则、权限和阈值，不能直接使用赛事模拟规则作运行依据。
